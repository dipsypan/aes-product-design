# AES产线下一代端点安全产品通用表单设计 Reference

## 调用契约

- 作为基础页面能力 Reference 使用。接收业务模型已确定的配置字段、字段属性、默认值、依赖关系、风险操作、`business_invariants`、`interaction_contracts` 和待确认项，不重新判断模块归属或业务模型。
- 前序skill已确定承载容器时，跳过本文档“步骤 1：容器形态决策”；其余步骤必须完整执行。
- 除调用方明确给出的业务专属规则外，完整执行本文档原有规则；不得删除、弱化或自行改写原有规则。
- 输出后将表单结构、标题层级映射、每个字段的 idux 组件与交互、选项说明分类、卡片组布局约束、默认值/校验和响应式要求汇总为 `visual_contracts`，并返回 `form_container`、`form_mode`、前置与后置待确认项、`regression_scope` 以及自检结果。
- 本 Reference 只定义通用表单能力，不得覆盖上游业务 Reference 已确定的保存、取消、返回、确认、权限和生命周期规则。
- 调整步骤、容器、表单分组或表单上下文时，必须显式说明受影响的上游交互契约，并将其加入 `regression_scope`；禁止因视觉结构变化删除或弱化既有行为。

	•	存在待确认点时，判断待确认点为前置确认点还是后置确认点。前置确认点要在方案输出前汇总确认，得到明确确认后才能开展生成。后置确认点先输出方案再统一汇总确认

【执行流程总览】
	•	分支 A（已知模块调整）：直接执行「步骤 3 组件选型」→「步骤 4 交互与排版规范」→「步骤 5 输出自检」
	•	分支 B（全新模块设计）：按顺序执行「步骤 1 容器决策」→「步骤 2 分层与布局决策」→「步骤 3 组件选型」→「步骤 4 交互与排版规范」→「步骤 5 输出自检」


步骤 1：容器形态决策

1.1 容器类型
	•	`full-page`：独立菜单级全屏页面。
	•	`drilldown-page`：从列表或详情进入的下钻页面。
	•	`form-modal`：从按钮、链接或行操作随时调取的表单弹窗。
	•	`confirm-modal` 只用于操作确认，不属于表单容器。
	•	抽屉不作为通用表单容器，不进入容器决策。任务中心现有新建抽屉属于存量特例，不得作为其他模块的参考；新增抽屉方案必须由用户明确指定并完成产品设计评审。

1.2 决策顺序
按以下顺序判断，命中后停止：
	1.	用户、上游业务模型或存量同类页面已明确容器时，直接采用。
	2.	独立菜单级配置模块使用 `full-page`。
	3.	从列表或详情进入，且存在多个分组、强字段依赖、复杂校验、分步流程、较长编辑任务、复杂资产配置或标准弹窗无法容纳的内容时，使用 `drilldown-page`。
	4.	从列表、详情或页面操作入口调取，且字段较少、分组少、逻辑与校验简单、可在较短时间内完成时，使用 `form-modal`。
	•	字段数量只作为辅助判断：表单项通常不超过 12 项时可考虑 `form-modal`，超过 12 项时应评估 `drilldown-page`；不得仅根据字段数量决定容器。
	•	表单项定义：1 个 label 对应 1 组交互组件，计为 1 项。
	•	用户未指定、上游未返回且无存量同类页面可参考时，将容器作为前置确认项。
	•	所有容器内的表单布局均遵循本 Skill；保存、取消、返回和确认由上游业务契约决定，容器规则不得擅自删改。
	•	上游已返回 `form_container` 时直接采用；`form_container: form-modal` 且已返回 `form_mode: create | edit` 时，继续执行 4.7。

1.3 输出契约

```yaml
form_container:
  type: full-page | drilldown-page | form-modal
  trigger: 表单入口
  decision_reasons: 容器选择依据
  reference_evidence: 真实参考页面或代码
  scroll_mode: page-scroll | body-scroll
  footer: 底部操作结构
  close_behavior: 关闭与 dirty 处理
```


步骤 2：分层与布局结构决策
按顺序逐层判断，输出结构方案
2.1 判断是否拆分步骤
	•	前置条件：所有配置项属于同一个任务流程
	•	满足任一条件 → 采用分步表单，跳过 2.2，直接进入 2.3： ① 表单项总数＞20 项，单页展示超过一屏（常规桌面端可视区） ② 存在强前置依赖：首步选项决定后续全部配置内容，且首步选项≥3 类，后续内容差异度＞80%
	•	不满足条件 / 不属于同一任务流程 → 采用单页表单，进入 2.2

2.2 判断是否启用左侧标签导航
	•	触发条件（同时满足）： ① 表单内存在 ≥4 个平行一级分类 ② 单个分类内表单项 ≥8 项（单分类内容超出常规桌面端可视一屏）
	•	满足条件 → 采用「左侧标签页定位 + 右侧表单内容」布局，参照附录样例 9
	•	不满足条件 → 没有左侧标签页定位，直接进入 2.3

2.3 判断内容默认呈现状态
	•	低频选填项（非核心配置、使用频率＜20%）统一放入「高级设置」模块
	•	高级设置默认收起，每次进入页面均保持收起状态，不记忆用户上次操作
	•	参照：附录样例 1

2.4 层级标题与分区规则
	•	先输出「标题层级映射」，列明标题、层级、父级和样式，再选择组件和编写页面。
	•	仅有一级标题时，使用「蓝色竖条 + 加粗文字」；存在两级标题时，一级标题保持该样式，二级标题仅使用加粗文字。禁止出现三级及以上标题。
	•	标题层级由内容关系决定，字号、组件尺寸和 HTML 标签不能代替一级 / 二级语义。
	•	同一标题只显示一次；公共组件已输出标题时直接复用，不得隐藏后再用普通文本模拟。
	•	一级标题、二级标题和 label 的文字起点统一；蓝色竖条位于文字左侧预留区域，不得改变标题文字起点。
	•	竖条尺寸、颜色和间距复用真实产品样式，不得自行定义。
	•	标题默认不增加背景、描边、卡片标题栏或横向分隔线；用户明确要求或真实参考页存在时除外，并记录 `reference_evidence`。
	•	示例：「基本信息、策略配置、分配对象」为一级标题；「策略配置」内的「客户端升级计划、规则库升级计划」为二级标题。

步骤 3：组件选型决策库
3.1 资产选择类（固定规则）
	•	资产选择场景 → 统一使用「选择资产」组件，参照附录样例 2

3.2 单选类（Radio / Select / 单选卡片）
决策顺序：先定基础形态，再升级样式
	•	基础形态判断（按选项数）： 选项数 ≤ 4 → 单选 Radio
	•	选项数 ＞ 4 → 单选 Select，超过8个选项时支持搜索下拉选项
	•	样式升级判断（按解释需求）： 仅个别选项需解释 → 选项后加「小 i 提示」
	•	所有选项均需解释，单条解释 ≤ 40 字 → 单选卡片（标题 + 短解释），参照附录样例 3
	•	所有选项均需解释，单条解释 ＞ 40 字 → 解释文案放在 label 后方，参照附录样例 4
	•	采用单选卡片时，同一选项组内所有卡片以内容最高的卡片为统一高度；内容变化、国际化文案变化或响应式换行后仍需重新满足等高
	•	卡片高度由完整内容自然撑开，禁止通过固定高度截断内容。标题、解释、链接及状态信息均允许自然换行，禁止省略号、单行截断、`line-clamp` 或隐藏溢出

3.3 多选类（CheckBox / 多选 Select / 多选卡片）
决策顺序：先定基础形态，再升级样式
	•	基础形态判断（按选项数）： 选项数 ≤ 4 → 复选框 CheckBox
	•	选项数 ＞ 4 → 多选 Select
	•	样式升级判断（按解释需求）： 仅个别选项需解释 → 选项后加「小 i 提示」
	•	所有选项均需解释，单条解释 ≤ 40 字 → 多选卡片（单选卡片样式改为多选交互），参照附录样例 3 衍生
	•	所有选项均需解释，单条解释 ＞ 40 字 → 解释文案放在 label 后方，参照附录样例 4 衍生
	•	采用多选卡片时，同样执行 3.2 的卡片等高、完整展示和响应式约束

3.4 功能启用类（Radio / Switch / CheckBox）
按场景精准匹配，无歧义
	•	规则 / 策略的启用 / 禁用状态配置 → 单选 Radio，参照附录样例 5
	•	功能总开关（开关控制下属多个配置项的显隐 / 可用状态） → 开关 Switch
	•	单一参数项勾选（无下属关联配置） → 复选框 CheckBox

3.5 输入类组件匹配表
| 组件类型 | 触发条件 | 典型场景 | 补充规则 |
| ---- | ---- | ---- | ---- |
| 基础输入框 Input | 单行单值输入，内容不限制为纯数字 | 策略名称、单个 IP / 域名 | 可搭配前置 / 后置标签，如域名前固定 https:// |
| 数字输入框 InputNumber | 仅输入数字值，支持步进调节 | 时长、文件大小、数量 | 单位处理：<br>1. 固定单位：参照附录样例 6<br>2. 可切换单位：参照附录样例 7 |
| 文本域 Textarea | 单条长文本输入，需多行展示 | 规则描述、详细备注 | 无用户指定时，默认限制输入 200 字符 |
| 行号输入框 ProTextarea | 批量输入同类型多条数据（≥5 条），每行一条 | 批量 IP、域名、手机号 | 参照附录样例 8 |


步骤 4：交互与排版通用规范
4.1 高效原则
（1）默认值与恢复默认
	•	默认规则：所有配置项必须设置推荐默认值；仅当配置会严重影响业务、或不同客户差异极大时，可无默认值。如用户输入时候没有提供默认值，可以作为后置待确认点跟进。在输出方案后，连同其他后置待确认点一起询问。
	•	模块整体恢复默认：当模块有通用推荐默认配置时，模块标题右侧通过分割线分隔，增加「恢复默认设置」按钮。交互逻辑，参照附录样例 10，点击按钮弹出气泡确认框。用户点击「确定」后，全模块恢复为初始默认值

（2）快捷入口与反显同步
	•	场景：配置过程中需调用其他模块的配置内容、或查看其他模块
	•	调用形式判断： ① 被调用模块为页面级 → 提供跳转入口，点击后打开新标签页并定位到对应模块 ② 被调用模块为弹窗级 → 优先在当前页面直接打开对应弹窗；无法实现时再采用跳转方案
	•	反显同步规则： ① 弹窗形式调用：修改后实时同步回原表单对应字段 ② 新页面跳转调用：若无法实现实时同步，在反显内容右侧增加「刷新」按钮，用户点击后同步最新配置

（3）选项记忆功能
	•	触发场景：存在前置控制项（Switch 开关、单选 Radio），且不同选项对应不同的子配置区域
	•	交互规则：用户切换选项时，保留当前选项下已填写的所有配置；再次切回该选项时，自动回填历史配置，不清空

4.2 简洁原则
（1）文案规则
	•	所有配置项 label、选项文案、描述文案均需精简凝练，避免冗余
	•	解释类文案默认收起，不默认展开大段说明

（2）解释说明全局统一规则
| 解释类型 | 放置位置 | 呈现形式 | 适用场景 |
| ---- | ---- | ---- | ---- |
| 字段概念解释 | label 后方 | 小 i 图标 | 解释单个配置项的定义、作用 |
| 选项含义解释 | 选项后方 | 小 i 图标 | 解释单个选项的具体含义 |
| 扩展说明（原理、更多方式） | label 后方 / 模块底部 | 蓝色文字链接 | 需扩大解释范围，如「运行原理」「更多规则」 |
| 业务结果或影响范围 | 对应字段下方 | 整行浅灰信息区 + 信息图标 | 用户提交前必须持续看见的生效范围、命中效果、风险或不可逆后果 |

解释说明必须先完成语义分类，再决定呈现位置：
	•	文案只解释一个选项的定义、适用对象、使用场景或选择建议时，归类为「选项含义解释」，放在该选项后的小 i 中；包含“适用于”“建议用于”“该选项表示”等措辞时默认命中此类
	•	用户把文案称为“说明”，不能据此直接外放；仍需根据它解释的是字段、单个选项还是整个模块进行分类
	•	只有用户明确要求常驻展示，或文案属于会影响当前操作决策且必须即时看见的风险 / 后果提示时，才允许外放；输出中必须写明外放依据
	•	业务结果或影响范围说明必须紧跟其对应字段、与输入区等宽，形成连续信息组；不得收进小 i、Tooltip 或 placeholder，也不得在中间插入标题或分隔线
	•	常驻信息区只承载当前选中状态产生的业务结果、影响范围、风险或不可逆后果，且必须满足“用户提交前需要持续看见”；文案必须与当前字段状态一致，切换选项后不再成立时必须同步更新或隐藏
	•	默认值、数量上限、输入格式、操作方法和普通校验说明不得使用常驻信息区，应由组件约束、校验反馈、小 i 或帮助文案承载
	•	同一信息已由选项文案、组件状态或校验反馈表达时，不得重复生成提示条
	•	仅个别选项需要解释时，即使其他选项没有说明，也不得为保持视觉对称将说明外放到选项下方
	•	示例：「适用于核心服务器、关键业务终端等对稳定性要求较高的资产」只解释“延迟更新”选项的适用场景，应放在该选项后的小 i 中，不常驻外放

（3）低频内容收敛
	•	非核心、低频使用的配置项统一收敛至「高级设置」模块，默认收起
	•	每次进入页面均保持收起状态，不记忆用户上次展开操作

4.3 防错原则
	•	触发场景：用户执行高风险操作（如关闭安全管控类核心功能、删除配置、恢复默认、清空批量配置等）
	•	交互规则：操作时弹出气泡确认框，用户点击「确认」后操作方可生效
	•	确认框需明确说明操作后果，避免模糊表述
	•	已有业务公共确认组件时，必须完整复用其组件、传参方式、内容结构和视觉样式，不得用自定义插槽、DOM 或局部样式重做气泡。AES 安全策略的 Switch 确认统一使用 `SwitchWithTooltip / SwitchControl` 的 `confirm-content` 字符串数组链路，只允许沿用既有 `confirm-icon` 插槽；禁止自定义 `confirmContent` / `title` 插槽以及宽度、字号、行高和按钮布局
	•	确认气泡属于浮层时，验收必须检查最终挂载位置下的计算样式和真实渲染尺寸；禁止仅检查 scoped CSS 声明。浮层脱离页面容器导致祖先选择器失效时，必须判定为失败

4.4 基础排版规范
	•	必填标记：必填 / 必选项，label 前加红色星标；未填写点击保存，统一提示「请输入此项」
	•	字段提示：配置项概念需解释原理时，label 后加「小 i 提示」（与 4.2 规则统一）
	•	同一模块内表单项垂直间距：8px，不同模块的标题和上一个模块最后的配置项的垂直间距为20px。注意如果采用单页表单时，不要复用BaseConfigForm布局里面的120PX间距。.base-info-form 高度应该为 auto。
	•	组件默认行高：32px
	•	label 与输入区最小间距：16px；同表单内以最长 label 宽度统一左对齐
	•	一级标题、二级标题和 label 都以第一个文字为基准左对齐。容器为弹窗时，距弹窗左侧 32px；容器为页面级别时，距页面内容区左侧 40px。

4.4.1 纵向布局对齐
	•	适用于纵向排列的 Radio、CheckBox、卡片、开关下属配置和其他多行控件。
	•	标准控件行中，label 与第一行 32px 控件垂直居中，不与整个内容组居中；后续各行与第一行控件左对齐。
	•	帮助文案和校验信息不得改变 label 与第一行控件的对齐；条件内容隐藏时同步移除占位和间距。
	•	自然高度卡片的 label 对齐第一张卡片的标题区域，不与整个卡片组居中。

4.4.2 横向布局对齐
	•	同一区域使用统一的 label 宽度和控件起点；一级标题、二级标题和 label 的文字起点统一。
	•	同行字段使用平台 Grid / Form 布局，不得使用独立 margin 拼接；同行控件保持相同高度和垂直中心线。
	•	响应式换行后，每个字段仍须保持自身 label 与控件的对齐关系。

4.4.3 行内组件对齐
	•	文字、Radio / CheckBox、Select / Input、单位、小 i 和链接组成同一逻辑行时，使用同一行容器并垂直居中，标准控件高度为 32px。
	•	不得使用带完整 label、默认间距或校验占位的嵌套表单项包裹行内控件；必须使用无布局字段绑定，或移除嵌套表单项的布局占位。
	•	空间不足时按完整语义组合换行，不得让 Select / Input 单独换行；小 i 和链接不得改变行高或挤偏相邻内容。

4.4.4 底部操作区按钮
	•	全屏页面、下钻页面和表单弹窗底部的「保存」「确定」「取消」「上一步」「下一步」等操作按钮，文字大小统一为 14px；不得使用小尺寸按钮或通过局部样式改为 12px。
	•	按钮名称、顺序和交互以上游业务契约为准；按钮高度、间距、模式和排列方式复用对应容器的平台规范。

4.5 卡片组验收规范
	•	同一选项组出现 2 张及以上卡片时，必须按最长标题、最长说明、带附加操作三类内容检查统一高度
	•	分别在项目目标桌面宽度和最窄支持宽度检查：卡片内容完整、文字自然换行、卡片之间等高、操作入口不溢出
	•	不能只检查 CSS 是否设置 `min-height`；必须以最终渲染结果确认所有同组选项卡片的实际高度一致

4.6 前端表单状态契约
	•	修改代码前按一级分组输出 `form_state_contract`：`group`、`value_path`、`registration`、`validation`、`dirty_source`、`change_tracking`、`serialization`。
	•	同一字段的初始化、读取、校验、dirty、变更确认和提交必须使用一致的数据路径；`id` 不得代替组件 API 中负责表单注册的 `name`。
	•	删除或替换 Stepper、Group、Card 等容器时，先确认原容器是否提供表单命名空间；改变命名空间时必须同步更新所有 `setValue/getValue/validate/trackChange/serialize` 路径。
	•	未通过项目通用表单项注册的手写字段，必须显式实现初始值、校验、dirty、可读变更记录和提交序列化，缺少任一项不得交付。
	•	纯视觉调整默认保持 `form_state_contract` 不变；确需改变时，自动把保存、取消、返回、复制和路由离开加入 `regression_scope`。

4.7 表单弹窗新增 / 编辑规范
	•	适用条件：`form_container: form-modal`。弹窗可由按钮、链接或行操作随时调取；新增返回 `form_mode: create`，编辑返回 `form_mode: edit`。
	•	表单弹窗仅承载字段较少、分组少、逻辑与校验简单且可在较短时间内完成的配置；不得承载步骤条、左侧定位导航或复杂大型配置区域。
	•	同一业务的新增和编辑必须复用同一字段顺序、分组体系和对齐网格，仅按业务契约改变批量能力、只读状态和默认值。
	•	默认采用单列布局。label 左对齐，同一表单内以最长 label 统一宽度；所有输入控件的起始位置和右边界对齐，并执行 4.4 的弹窗边距、行高和间距规则。
	•	基础字段直接顺序排列，不为少量字段增加“基础配置”等无信息量标题。只有存在 2 个及以上强关联字段、且需要与其他字段表达独立业务语义时才建立分组；分组标题层级和样式继续执行 2.4。
	•	使用 `ProTextarea` 批量输入同类对象时，输入区宽度占满表单内容区，显示行号，默认保证 8-10 行可见；格式帮助按 4.2 分类，不能用普通单行输入替代。
	•	条件字段隐藏时必须同步取消注册或校验、清除不应提交的残留值并立即收起空间；重新显示时按业务要求恢复记忆值或默认值。显隐前后不得残留空白占位。
	•	内容超高时仅表单主体滚动，标题区和底部操作区保持稳定；弹窗尺寸、内边距和滚动方式复用平台规范。
	•	底部操作区默认右对齐，主按钮“确定”在前、次按钮“取消”在后，按钮文字为 14px。上游业务模型已规定按钮名称、顺序或提交行为时以上游契约为准，本 Skill 不得改写。
	•	点击确定先校验全部当前可见且已注册字段；提交期间主按钮显示加载并防止重复提交。成功、失败、部分成功及列表上下文保持方式由上游业务模型定义。
	•	取消、右上角关闭和遮罩关闭共享同一个退出入口与 dirty 判断：无修改直接关闭；有修改弹出放弃修改确认。上游明确禁止遮罩关闭时关闭该入口，但取消和右上角关闭仍使用相同脏值保护。
	•	编辑表单必须在数据加载完成后建立 initial snapshot；动态字段、只读字段和外部选择器的变化均按 `form_state_contract` 纳入 dirty、变更追踪和提交序列化。
