# AES 模块注册表

## 产品背景

深信服下一代端点安全是集病毒查杀、高级威胁检测与响应、策略管理于一体的终端安全平台。

使用本文件判断能力归属，不要求用户了解产品菜单。路由时比较业务对象、治理模型和生效链路，不仅比较页面名称。

## 通用判断原则

- 优先扩展已有模块，避免为单个配置能力建立重复治理模型。
- 独立菜单不是需求起点，而是独立业务对象和治理模型的结果。
- 新增分类、配置项、字段或交互不等于新模块。
- 新模块必须说明现有模块不能承载的原因。

## 候选 1：已有安全策略

### 模块定位

安全策略统一配置终端安全防护能力，并根据策略状态、优先级、分配对象和排除对象决定终端最终生效配置。可复用治理模型同时包含优先级语义、内置策略约束及列表排序行为。策略由平台同步至终端 Agent，通常在 10 秒内生效。

典型能力边界：

- 基础配置：客户端基础行为、自保护、通知等
- 安全配置：隔离区与信任区管理及终端用户权限
- 病毒防御：病毒扫描、实时防护、威胁情报联动、AI 分析
- 高级威胁：端点事件及进程、网络、文件、注册表等行为采集

### 正向证据

| 业务事实 | 分值 |
| --- | ---: |
| 控制终端防护、检测、采集、隔离、信任或客户端行为 | +3 |
| 配置需要下发至终端 Agent 后生效 | +2 |
| 可复用状态、优先级、分配对象和排除对象 | +3 |
| 只是增加参数、配置项或一至三级能力分类 | +2 |
| 与现有四类能力边界直接相关 | +2 |

### 排除证据

- 需要完全不同的管理对象或生效主体
- 需要独立审批、权限、授权或冲突解决模型
- 同一安全策略内无法表达其配置实例与适用范围

### 分发

- 业务模型：`policy-management-existing.md`
- AES 列表模板：`../templates/list.md`，仅在涉及列表、搜索、筛选或排序时与公共列表框架成对读取
- AES 表单模板：`../templates/form.md`，仅在涉及配置项和交互时与公共表单框架成对读取
- 前端验收：`../acceptance/frontend.md`，`delivery_scope` 包含 `frontend` 时在代码修改完成后读取

## 候选 2：全新独立策略模块

### 模块定位

为无法复用现有安全策略治理模型的能力建立独立策略对象、页面和生命周期。新模块通常具有自己的策略列表、创建/编辑、状态、优先级、分配、生效和权限规则。

### 正向证据

| 业务事实 | 分值 |
| --- | ---: |
| 需要创建多条独立策略并分别管理 | +3 |
| 需要独立列表、详情、复制、删除和生命周期 | +3 |
| 具有不同于安全策略的分配、生效或冲突规则 | +3 |
| 具有独立权限、审批或授权模型 | +2 |
| 管理对象不是终端安全防护配置 | +3 |

### 弱证据

以下内容单独出现时不得判定为新模块：

- 用户说“新增策略”“新增页面”
- 希望入口更明显
- 配置项数量暂时较多
- 现有页面需要新增一级分类

### 分发

- 业务模型：`policy-management-new.md`
- AES 列表模板：`../templates/list.md`，仅在涉及列表、搜索、筛选或排序时与公共列表框架成对读取
- AES 表单模板：业务模型完成后与公共表单框架成对读取 `../templates/form.md`
- 前端验收：`../acceptance/frontend.md`，`delivery_scope` 包含 `frontend` 时在代码修改完成后读取

## 关键未知项

只有以下未知项可能改变路由，允许作为前置问题：

1. 是否需要创建多条独立配置实例并分别分配对象？
2. 是否可以沿用安全策略的优先级、分配对象和排除对象？
3. 是否存在独立审批、权限、授权、生效或冲突规则？

不要询问用户菜单应该放在哪里。先基于现有证据推荐位置，再询问上述业务事实。

## 扩展格式

新增产品模块时追加一个候选章节，并至少定义：

```yaml
module_id: 稳定唯一标识
module_name: 用户可见名称
business_object: 核心业务对象
capability_boundary: 可承载能力
governance_model: 状态、优先级语义、内置对象约束、分配、排序、权限和生命周期
effective_path: 配置或操作如何生效
positive_evidence: 带权重的归属信号
exclusion_evidence: 明确不归属的信号
business_reference: 业务规则文件
common_references: 按条件读取的通用规则文件
acceptance_reference: 前端交付完成后必须执行的验收规则文件
```

保持所有 Reference 由本入口直接引用，避免 Reference 间多层跳转。
