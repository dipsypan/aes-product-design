- 接收路由入口提供的结构化上下文包，不重新判断模块归属。

- 本 Reference 负责策略模型与页面级规则；“策略配置”内的通用表单结构、组件、交互与排版，由入口继续读取 `../templates/form.md` 完成。

- 组件默认高度 32px；通用表单规则以 `../templates/form.md` 为准，冲突优先级：业务专属规则 > 表单通用规则。
- 所有样式参照均以产品现有页面为准，不得自行演绎样式效果。
- 前端实现或后续调优时，必须从真实安全策略页面和当前代码提取保存、取消、返回、校验、脏值、页面离开保护及本次涉及的开关确认等既有行为，返回为 `interaction_contracts`；不得因只修改「策略配置」而省略页面级生命周期。
- 开关二次确认属于低自由度既有模式：必须复用真实安全策略页面中的公共开关确认组件、传参方式、内容结构和视觉样式；禁止仅复用组件名称后改用自定义插槽、DOM 或局部样式重做确认气泡。
- 修改容器、步骤、表单分组、表单上下文、数据结构或路由守卫时，将上述既有行为加入 `regression_scope`，并由入口调用 `../acceptance/frontend.md` 验证。

## 模块定位与信息架构
1、模块定位：统一配置终端安全防护能力，通过状态、优先级、分配 / 排除对象决定终端生效配置，覆盖客户端行为、隔离 / 信任区、病毒防御、高级威胁采集等能力。

2、资产平台分区
- 策略列表顶部按“系统类型 × 资产类型”的已支持组合显示路由标签；系统类型包括 Windows、Linux、macOS，资产类型包括 PC、服务器。
- 当前仅支持「Windows PC」「Windows 服务器」，只显示这两个标签；禁止按维度自动生成尚未支持的组合。
- 每个标签页下仅查询和展示该“系统类型 × 资产类型”组合的策略，禁止跨组合混用策略数据。
- 新增一个受支持的组合属于页面级扩展，必须按“新增顶部标签及路由 → 建立该组合的策略列表和平台上下文 → 设计该组合的策略配置”顺序执行；禁止跳过标签页和列表，直接新增策略配置内容。
- 新组合必须同步补齐列表及新增 / 编辑路由；标签切换后进入对应列表，直接访问或刷新路由时仍保持正确标签，新增 / 编辑完成或返回时回到原组合列表。
- 从任一标签页新建策略时，新增策略页的系统类型必须默认继承当前标签对应的平台值（如「Windows PC」对应 `windows-pc`）；禁止使用固定默认值或沿用其他标签的平台值。
- 新增 / 编辑安全策略时，策略配置左侧父级导航右上角必须显示当前平台标签；该标签以详情页 `basicInfo.platform` 为准，新建时由列表页传入的平台值初始化，编辑时由策略数据回填，三者必须一致。该标签是当前平台上下文的只读展示，不得单独切换。
- 标签名称必须同时表达系统类型和资产类型，并沿用现有命名格式。

3、页面构成
1）策略列表页：策略浏览、筛选、排序、批量操作、单条操作
2）策略详情页：编辑策略内容，含「基本信息、策略配置、分配对象」3 个模块
| 策略详情模块 | 含义 |
| ---- | ---- |
| 1.基本信息 | 策略名称、描述等与实际生效能力无直接相关的参数 |
| 2.策略配置 | 策略真正生效的能力配置参数内容 |
| 3. 分配对象 | 这个策略作用于哪些对象 |

## 修改约束
1.无明确指令时，仅修改「策略配置」模块，禁止改动「基本信息」「分配对象」。
2.设计样式与交互逻辑优先复用现有安全策略的已有模式。
3.策略配置分类分层模式（所有平台通用）
| 层级 | 判定标准 | Windows 示例（仅示意） |
| ---- | ---- | ---- |
| 一级分类 | 按稳定的业务目标或安全能力域聚合，呈现为左侧主菜单 | 基础配置、病毒防御、高级威胁 |
| 二级分类 | 一级分类下可被用户独立定位和配置的业务主题，呈现为左侧子菜单 + 右侧卡片 | 客户端自保护、病毒扫描、端点事件采集 |
| 三级分类 | 二级分类下具有独立业务作用、启停状态或成组参数的具体能力，呈现为卡片内功能项 | C2 自动封堵、进程行为采集 |

- 分类名称必须表达业务能力，不得使用「开关配置」「输入框配置」等组件名称。
- 普通参数直接归入所属二级或三级能力，不得为凑层级单独建类；没有独立三级能力时允许止于二级分类。
- 同一能力只归入一个分类路径；存在依赖关系时在配置项规则中表达，不得重复归类。

## 策略治理不变量

仅当需求涉及策略列表、优先级或默认策略时应用，不扩大仅修改「策略配置」的需求范围：

- 优先级数值 `1` 表示最高优先级，数值越小，业务优先级越高；列表默认按业务优先级从高到低显示，对应 `priority ASC`。
- 内置默认策略的业务优先级永远最低，因此始终位于所有非内置策略之后；禁止删除、禁用或调整其优先级。
- 涉及列表排序时，「优先级」「创建时间」「最近修改时间」表头必须呈现并实现既有排序交互；时间首次排序默认最新在前。
- 搜索、快速筛选和排序可组合生效，任何排序都不得破坏内置策略最低优先级的不变量。
- 返回 `design_capabilities: [list, search, filter, sort]`，由入口读取 `../templates/list.md`；参考证据为安全策略真实列表页和项目既有实现。

步骤 A2：新增分类处理
（1）新增一级分类
	•	左侧新增可展开的一级导航，并在策略配置注册表中新增对应分组。
	•	一级分组必须至少包含一个二级配置卡片；未提供二级名称时，可建议使用与一级分类相同的名称，但必须标记为待确认。
	•	同步配置该分组的权限、平台支持范围和空分组过滤规则。

（2）新增二级分类
	•	在对应一级导航下新增二级子菜单。
	•	新增独立配置卡片，并注册卡片组件、表单数据路径、变更处理函数、平台支持范围和权限规则。
	•	点击二级菜单时滚动定位到对应卡片；卡片标题和布局复用现有业务卡片模式。
	•	只有参考卡片已有恢复默认行为时才复用该行为，不得默认给所有卡片增加恢复默认按钮。

（3）新增三级能力
	•	在二级卡片内部新增功能组或配置项，不新增左侧导航。
	•	根据能力语义选择 Switch、Checkbox、Radio、输入框等控件，并补齐联动、校验、提示和变更记录。

### 流程 B：全新平台组合扩展与建模

步骤 B1：先扩展资产平台入口。新增顶部路由标签、该组合专属策略列表、平台上下文及新增 / 编辑 / 返回链路，并确保列表请求只携带当前组合的平台值。完成此步骤后才能设计策略配置模块；即使需求重点只描述配置内容，也不得省略本步骤。

步骤 B2：从用户输入提取能力清单。每项至少识别能力名称、业务目的和需要配置的参数；默认值、安全影响、依赖关系未提供时标记为待确认，禁止引用 Windows 值补全。

步骤 B3：将分类树映射到现有策略配置页面。
	•	策略配置位于策略详情页的「策略配置」步骤，不能改变「基本信息」和「分配对象」步骤。
	•	一级分类映射为左侧可展开的父级导航和一个内容分组。
	•	二级分类映射为父级导航下的子菜单和右侧独立卡片。
	•	当前一级分类下的二级卡片纵向展示；点击二级菜单时滚动定位到对应卡片，不替换整个右侧内容。
	•	三级能力及其参数放在对应卡片内部，不新增左侧导航。
	•	根据平台、权限、默认策略状态和条件显示规则动态过滤卡片；过滤后没有卡片的一级分类不得展示。

步骤 B4：实现全新平台的配置卡片。
	•	根据用户输入为每个二级配置主题设计独立卡片；Windows 卡片只能作为布局和交互参照。
	•	每个卡片必须接入平台策略配置注册表，并声明 `key`、`label`、`component`、`dataIndex`、`changeHandler`、`supportedPlatforms`。
	•	同步设计该平台的默认值、校验、字段联动、风险提示、变更记录和恢复默认规则。
	•	未提供的业务默认值、安全影响和依赖关系不得引用 Windows 值，需标记为待确认。

步骤 B5：将每个配置项继续交给下方通用设计步骤；只有业务语义明确相同时才能复用已有专属规则，否则读取 `../templates/form.md` 选择组件，并输出待确认的业务默认值或风险规则。

### 通用配置项设计

步骤 3：配置项设计规则
仅在用户输入与以下业务语义明确匹配时使用对应专属规则；其中 Windows 示例和默认值不得自动继承到全新平台。未覆盖场景由入口读取 `../templates/form.md` 补充组件选型规则。

3.1 功能启禁用配置
1）独立能力启禁用：使用 Switch 开关
适用：具有独立业务作用、需要明确开启 / 关闭的能力，不以其所在分类层级作为组件判断依据（如 C2 自动封堵、客户端 AI 解读）。

| 细分类型 | 默认状态 | 常态展示规则 | 二次确认交互 | 切换后文案规则 | 参考示例 |
| -------- | -------- | ------------ | ------------ | -------------- | -------- |
| 默认开启（安全价值型） | 开启 | 开关 + 功能名称描述；<br>下方固定文案模板：<br>`建议始终开启。开启后，{主体}会{直接效果}，{安全相关影响}` | 点击关闭时弹出二次确认：<br>`关闭后，将{消极影响（开启文案反向表述）}。确定要关闭吗？` | 关闭后文案沿用二次确认内容，去掉「确定要关闭吗」 | C2 自动封堵、文件实时防护 |

开关二次确认前端实现约束（强制）：
	• 先从当前安全策略代码中选择同方向风险的真实参考开关：关闭前确认优先参考「C2 自动封堵」或「文件实时防护」，开启前确认优先参考「客户端调试模式」。
	• 使用项目公共 `SwitchWithTooltip / SwitchControl` 链路；确认文案通过 `confirm-content` 字符串数组传入，只允许沿用既有 `confirm-icon` 插槽。
	• 禁止自定义 `confirmContent` / `title` 插槽、确认框 DOM、标题层级、宽度、字号、行高、内边距或按钮布局。用户明确要求改变且提供真实产品参考证据时除外，并须列为前置确认项。
	• 确认文案直接按既有正文行展示，不额外增加加粗标题。长文案由公共确认气泡按既有宽度自然换行，不得用 `max-width` 或浮层外部祖先选择器替代公共样式。
	• `interaction_contracts` 必须覆盖触发、取消、确认和状态变化；`acceptance_checks` 必须在运行态对比参考开关的气泡宽度、字号、行高、换行、图标和按钮布局，不能用静态代码检查代替。
