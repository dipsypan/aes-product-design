# 前端交付验收 Reference

## 定位

作为策略设计路由的最终交付门禁。只负责把上游业务与设计契约转成可执行检查、运行前端并记录证据；不重新判断模块归属，不补写业务规则，不改变设计方案。

`delivery_scope` 为 `frontend` 或 `design-and-frontend` 时必须执行。方案交付但不修改前端时不执行。

## 输入契约

必须接收：

```yaml
target_urls: 待验证页面及进入方式
page_inventory: 页面、模式和关键状态
business_invariants: 不得破坏的业务规则
interaction_contracts: 前置状态、动作、预期结果和失败反馈
form_state_contract: 涉及表单时，各分组的路径、注册、校验、dirty、变更追踪和提交映射
visual_contracts: 标题、组件、布局、响应式和文案规则
reference_evidence: 真实参考页与项目代码证据
acceptance_checks: 上游生成的可执行验收项
regression_scope: 本次修改可能影响的既有行为
changed_files: 实际修改文件
```

缺少 `business_invariants`、`interaction_contracts`、`acceptance_checks` 或 `regression_scope`，以及表单任务缺少 `form_state_contract` 时，不得自行猜测；返回 `status: blocked` 并要求入口补齐上下文。

## 执行原则

1. 以用户需求和业务 Reference 为验收真值，通用设计规则不得覆盖业务不变量。
2. 验收真实运行结果，不以代码存在、静态推断、编译成功或 HTTP 200 代替交互结果。
3. 优先使用项目已有测试、浏览器控制和真实参考页面；只有无法运行时才做静态检查，并将对应行为标记为未验证。
4. 只在用户提供的本地、演示或 Mock 环境执行会写数据的操作；不得向生产环境提交测试数据。
5. 保留工作区原有改动，不通过回退无关代码制造通过结果。

## 执行流程

### 1. 建立追踪矩阵

编辑或验收前生成内部矩阵：

| 规则来源 | 验收项 | 代码位置 | 修改影响 | 验证方式 | 结果证据 |
| --- | --- | --- | --- | --- | --- |

矩阵必须覆盖用户本轮需求、`business_invariants`、`interaction_contracts`、`acceptance_checks` 和 `regression_scope`。同一行为由多处规则约束时合并验证，不遗漏来源。

### 2. 静态与构建检查

按项目能力执行：

- 修改文件的格式、Lint、类型和构建检查。
- 路由、组件导入、Mock、国际化键和请求字段的一致性检查。
- 表单容器、步骤或分组变化时，核对字段注册、取值、校验、dirty 状态和路由守卫仍有完整链路。
- 业务 Reference 要求复用公共交互模式时，核对目标实现使用了与真实参考代码相同的组件和传参链路。发现自定义插槽、DOM 或视觉样式绕过公共实现且没有用户确认与参考证据时，直接记录为失败。

静态检查只用于提前发现错误，不产生最终 `passed` 结论。

### 3. 运行环境检查

- 按工程说明启动正确的入口服务、目标微应用及必要依赖。
- 验证页面入口、共享依赖和关键异步资源来自预期服务。
- 检查页面是否可见、控制台是否存在阻断错误、关键资源是否加载失败。
- 修复开发代理时限制影响范围，并回归至少一个同应用既有页面；禁止仅验证目标资源返回 200。

### 4. 行为验收

逐项执行上游交互契约。表单页面至少覆盖：

- 初始值与编辑/复制回填。
- 条件显隐、选项切换记忆、关联入口和刷新反显。
- 必填与格式错误时的保存反馈及请求阻断。
- 校验通过后的确认、确认取消、确认提交、成功反馈和返回位置。
- 无修改取消、修改后取消、确认留在页面、确认放弃。
- 未保存状态下通过返回按钮和路由离开的保护。
- 内置对象、权限、禁用状态等业务限制。

存在多个一级表单分组时，必须执行字段链路抽样，不得只验证一个分组：

- 每个一级分组至少修改一个已注册字段，编辑确认弹窗必须出现对应分组和字段。
- 同时修改所有一级分组各一个字段，确认弹窗不得漏组、漏项或混入未修改项。
- 任一分组的修改都必须触发 dirty、取消确认和路由离开保护。
- 新增与复制必须确认全量配置；复制提交后还要验证新增记录、源对象不变、默认值和最终列表顺序。

列表页面按上游能力覆盖搜索、快速筛选、排序、分页、操作确认以及业务不变量组合生效。

### 5. 视觉与响应式验收

- 在项目目标桌面宽度和最窄支持宽度检查布局。
- 核对标题层级、组件类型、间距、对齐、文案、Tooltip 和空状态。
- 卡片组必须比较最终渲染高度，确认完整换行、等高且无截断；只检查 CSS 属性不算通过。
- 检查表头、搜索区、固定操作区和动态内容没有遮挡、溢出或异常空白。
- 对 Tooltip、Popconfirm 等浮层执行真实触发，不以组件存在或 CSS 声明代替运行结果；对比参考页面的最终宽度、字号、行高、换行、图标、按钮布局和相对位置。
- 浮层由 Portal / Teleport 挂载到页面容器外时，检查最终计算样式是否实际命中。scoped 样式依赖原容器祖先而失效、长文案撑宽浮层或继承到异常字号时，必须判定为失败。
- AES 安全策略的 Switch 二次确认需与「C2 自动封堵」「文件实时防护」或「客户端调试模式」中的同方向确认气泡对比；确认使用公共 `confirm-content` 链路，且不存在未经确认的自定义确认内容插槽和气泡样式。

### 6. 回归与闭环

- 对 `regression_scope` 逐项回归，不只验证本轮新增效果。
- 发现失败时定位原因、修复并重新执行相关检查；在同一任务内持续到通过或出现真实阻塞。
- 无法访问浏览器、缺少服务或测试会产生不可接受的数据影响时，将对应项记为 `unverified`，整体返回 `blocked`，不得返回 `passed`。

## 结果契约

```yaml
status: passed | failed | blocked
checks:
  - requirement: 验收规则
    source: 用户需求或 Reference
    result: passed | failed | unverified
    evidence: 实际操作、截图、日志或测试输出
failures: 失败项、原因和对应代码位置
unverified: 未验证项及阻塞原因
regressions: 回归检查结果
changed_files: 实际修改文件
```

判定规则：

- `passed`：所有关键业务、交互和回归项均有运行证据且通过。
- `failed`：存在已复现但尚未修复的失败项。
- `blocked`：存在关键未验证项，无法证明交付满足契约。

## 输出门禁

- 只有 `status: passed` 时，入口才能声明前端交付完成。
- `failed` 时返回修复流程，不把问题转交用户重复描述。
- `blocked` 时明确缺失权限、环境、服务或数据条件，并列出恢复验证所需的最小动作。
- 最终汇报必须区分“已验证通过”“静态检查通过”和“未验证”，禁止模糊表述。
